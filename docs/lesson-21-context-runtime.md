# 第 21 课 · Context Runtime 与 PromptOps

两次演示各改变一个条件。第一题保持问题和提示词版本相同，换部门身份。第二题保持身份、问题和业务事实相同，只发布一个新提示词版本。两张卡都在新建分析的输入框下，点击后手动发送。

## 第一题 · 同一句“销售额”，我部门怎么算？

> 周会只写了“销售额”，同事问我这个数到底算的是什么。请按我所在部门平时采用的口径，核对 2025-11-17 至 2025-11-23 的销售额。告诉我指标的正式名称、哪件业务发生时才算入，以及本周哪一天金额最高、当天多少。再挑最早的一个最高日，看看当天哪个渠道贡献最大、贡献了多少。请把口径来源和本次查到的日数据分开说明；如果有并列最高或某天数据未齐，请标出来。

**课前准备**　选用已经发布零售经营语义和查询绑定的租户 101 教学工作区。准备销售部、财务部各一个可分析的身份，两者使用相同的数据可见范围，每个身份只命中一个部门默认口径。本演示使用启用经营语义 Registry、关闭跨源检索模式的教学工作区，便于在第一步看到带部门口径解析的完整摘要。讲师在「指标口径」核对下面两个部门默认项，并确认两种指标的按日查询可用。[教学数据的默认项](../apps/web/db/main/seeds/retail-v1/edition.json)

| 观察点                 | 销售部应看到                               | 财务部应看到                                         |
| ---------------------- | ------------------------------------------ | ---------------------------------------------------- |
| 已发布的部门默认值     | 支付 GMV（`sales.paid_gmv`）               | 确认收入（`finance.recognized_revenue`）             |
| 回答里应说清的业务差异 | 按成功支付事件的发生时间归属，失败支付排除 | 按收入分录的确认时间归属，妥投确认收入、受理退货冲减 |
| 执行时取得的事实       | 按日的支付 GMV、最高日及金额               | 按日的确认收入、最高日及金额                         |

**现场操作**　两个身份分别新开会话，原样发送第一题。先遮住执行时间线，让学员仅凭两份回答辨认哪份属于财务部。题面没有给出任何部门名称、指标代码或业务事件。两个最高日即使恰巧相同，也可以用“成功支付”和“妥投／受理退货”区分口径。

**再展开运行过程**　在首次取数前，Context Runtime 已将本次身份可见的已发布语义摘要装入上下文。若教学环境允许查看准备帧，展开这一帧的 `publishedSemanticRegistry.authorized_resolution`（来源标记为 `publishedSemanticRegistry` 的对象中的 `authorized_resolution` 字段），对照两份答案的指标名称；随后查询回执才提供日期、渠道和金额。看执行时间线中这轮 `resolve_semantics` 回执如何把原话“销售额”落到具体口径，再看 `query_metric` 按该口径读取的每日金额和数据状态。在 Langfuse 中可用 `context.assemble` 对照装配步骤，用 `compass.tool.execute` 定位实际调用。最高日来自第一份按日回执。继续在时间线查看该日的渠道分组回执，核对第二次取数的日期是否就是上一步找到的最高日，再核查渠道和金额。若模型一次获取日与渠道的交叉明细，则从同一回执按日加总并核查最高日的渠道排序。默认口径来自工作区发布配置；日金额随实际查询返回。若出现口径选择卡，先核对身份的部门归属与默认项；遇到数据缺口时，记录缺口及对结论的影响。

## 第二题 · 这笔实付能写进周会定稿吗？

> 周会材料明早要发。渠道同事发来一份 POS 日报，实付合计 14,108.89 元；支付团队的对账回执还没到。填报人想把这个数写进“已核对实付”栏。请给我一段可以直接转发给填报人的处理意见。

**第一次运行**　保持当前发布版，用同一教学账号和指定模型新开会话发送第二题。保存原回答，确认任务归入经营问答，并在 `context.assemble` 的 `prompts_used` 中找到 `tasks/business_qa/system.md`，记下它的文件版本。原答的措辞以现场输出为准。场景中的金额和回执状态均由双方共享，比较重点是运营人员拿到答复以后可以做什么。

**讲师手动发布**　在独立教学环境的 Prompts 管理页打开 [tasks/business_qa/system.md](../apps/agent/src/compass_agent/prompts/tasks/business_qa/system.md)。保留原文，追加下面这段教学用的填报规则，点击「保存草稿」和「发布此文件」。该文件适用于经营问答，独立教学环境可避免影响其他团队。

> 回复填报或定稿请求时，按“填报处置单”交付。第一行固定为「填报处置单」。接着写「当前状态」「本次填写」「解除条件」三项。凡指定栏位要求核对、实际仍缺少对方回执，当前状态写「待对账」；说明金额现在可放在哪个栏位、哪个栏位要留空；最后写明由谁提供什么材料、核对哪些项目后才可转为已核对。本教学工作区约定：未对账金额达到 10,000 元，答复中明确标为「转经营复核」，由运营负责人跟进支付回执；低于 10,000 元由填报人跟进。只给处置意见。

**第二次运行**　保持账号、模型和数据条件，再开空白会话，原样点第二张卡。两份答复都应保留 14,108.89 元和缺回执这两个事实。发布后的答复应从一般处理意见变成可执行的处置单：标出「待对账」，给出题面没有提及的处置决定「转经营复核」及负责人，把金额放在“渠道日报报数”之类的暂记栏，留空“已核对实付”，并要求支付团队补回执、核对渠道、期间和金额。关键判分点是 14,108.89 元触发了新发布的万元分流规则。只换标题、遗漏转交对象，记为未通过。再核对两次 Run 的文件版本。演示结束后，把原版本恢复为草稿并发布。历史会话可继续用于对照。[本机管理入口](http://127.0.0.1:8100/platform/promptops)

首页题面在 [support/starters/analysis.json](../apps/agent/src/compass_agent/prompts/support/starters/analysis.json)。部署新版卡片时，在 Prompts 中核对并发布这份题集；课堂第二题的 A/B 实验只编辑经营问答系统提示词。
