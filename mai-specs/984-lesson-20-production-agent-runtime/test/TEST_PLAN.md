## 双角色定稿的业务验收

2026-11-15 建立，2026-11-16 补充复审验收。适用于同一个 `apps/agent` 镜像的两个部署角色。标准验收环境运行一个 Scheduler 和两个 Agent 副本，共用隔离的 PostgreSQL 和 Redis。Scheduler 只处理到期、交付重试和状态同步，Agent 统一负责即时与定时 Run 的准入、配额、公平领取和执行。TC-22～TC-38 的执行结果见 [双角色验收](ACCEPTANCE.md#双角色版本--2026-11-16)。历史 TC-01～TC-21 保留原编号和运行条件，复用适用的业务断言。

### TC-22：Web 和 Chat 管理同一计划

- 关联：AC-12、AC-15、AC-16，评审 R5、R6。
- 操作：普通所有者在 Web 创建计划，在 Chat 查询、确认修改和查看执行记录，再返回 Web 核对计划 ID 和版本。另在 Chat 创建，回 Web 编辑、停用和删除。覆盖搜索、筛选、Cron 预览、同名消歧、取消确认、Web 提交失败、跨入口用旧版本更新和历史跳转。普通成员与管理员分别批准一项业务 Action，对照计划所有者确认权限。
- 预期：两个入口读取同一份持久计划。普通所有者能确认自己的计划变更，既有业务动作遵守原审批权。取消确认或已过期版本无法产生写入，删除保留获授权的执行记录。跨工作区、租户及同工作区其他成员无法查看、伪造确认或改写该所有者的计划。
- 验证：真实浏览器、Chat 工具回执、API 和历史记录。保存计划 ID、版本序列、桌面与窄屏交互、焦点与错误反馈以及实际持久写入计数。

### TC-23：Chat 确认后的取消、过期与写入争用

- 关联：AC-06、AC-12、AC-15、AC-19，评审 R6、R7。
- 操作：所有者确认 Chat 修改，冻结批准后的实际写入。分别在另一入口先改计划、从另一 Agent 先取消 Run、让执行租约失效并由其他 Agent 接管，再放行旧请求。交换获胜顺序，另在计划写入与 Action 回执已提交时终止执行进程并重放原请求。
- 预期：旧版本、已取消 Run、非当前执行世代无法形成首次写入。若授权写事务先提交，计划变化与 Action 效果回执原子可见，后续重放返回已提交结果而无第二次写入。
- 验证：取消受理及提交的先后、两个执行世代、计划版本和 Action ID，按真实 PG 事务窗口核对。

### TC-24：Scheduler 单独停机、替换和过期写入

- 关联：AC-01、AC-13、AC-16、AC-19，评审 R8、R10、R12。
- 操作：在到期扫描提交的事务前后分别终止 Scheduler，期间继续提交即时 Run 并观察已入队 Run。启动替代实例，模拟多次漏跑与短时重复启动。使原 Scheduler 的写者租约过期后恢复旧进程，尝试扫描、提交旧触发和覆盖状态。另测时区与夏令时边界。
- 预期：在途 Run 与新即时 Run 按原流程运行。Scheduler 恢复后遵守漏跑合并规则，每个应交付时刻仅一个触发。旧写者与非 Scheduler 凭据均无法新增或推进触发，已提交的接单记录保持。重复或不存在的本地时刻符合正式规则。
- 验证：真实进程和同库状态，记录原/新写者、(计划 ID, 计划触发时刻)、触发记录数及各 Run 的执行结果。

### TC-25：交付、接单和关联原子提交

- 关联：AC-05、AC-13、AC-16，评审 R8。
- 操作：用稳定触发 ID 提交同一触发，在 Agent 接单事务提交前后分别中断服务或丢弃 HTTP 回执。切换到另一 Agent 后重试。重复试验，在已接单但调用方未收到回执期间软删除对应会话，再恢复 Scheduler。
- 预期：提交前中断无半成品。提交后一条触发只关联一个 Run，Run、job、受理回执、Outbox 和触发关联一起可见。重试不会生成额外 Run。软删除只影响用户可见的会话内容，内部交付核对仍可确认原结果。
- 验证：真实 HTTP、同库事务记录、两个 Agent 身份、回执 ID 和模型/工具调用计数。

### TC-26：统一准入、交付退避和权限撤回

- 关联：AC-07、AC-14、AC-15、AC-16、AC-18，评审 R5、R10。
- 操作：同一租户并发提交大量到期计划与即时 Run，使 Agent 返回 429，同时保持另一租户的即时与定时请求。核对 Scheduler 的重试时间与 `Retry-After`。释放容量后以同触发 ID 再交付。另覆盖次数/期限耗尽、提交结果未知、已开始退避时删除计划、暂停/待审批占用到下一次到期，以及撤回计划管理权或 Run 执行权。
- 预期：即时与定时 Run 使用同一套 Agent 配额、背压和公平领取规则。Scheduler 把受限触发延期，继续处理其他就绪记录。重试不早于 `Retry-After`，期限内继续有限尝试。终止前确认无已受理 Run，结果仍未知时保留待核对状态。删除和停用之前已开始的交付按原快照及期限收口，未开始触发按规则跳过。同计划最多一条未结束执行或待交付链路，撤权后的新交付无法接单。历史显示本次触发、退避原因和下次重试时间。
- 验证：保留即时/定时来源、请求 ID、接单/拒绝记录、各租户在途/积压计数、开始/重试/跳过/到期时间、调度状态和授权结果。

### TC-27：双副本并行、跨副本控制与二次接管

- 关联：AC-03～AC-07、AC-18、AC-19，评审 R6、R7、R12。
- 操作：在小夹具显式配置每副本一槽、集群两槽及每租户一槽，使用两个租户和相同上游容量。在一个与两个副本时运行相同负载。留住 A 副本正在执行的可恢复 Run，从 B 接收暂停/取消，再在新样本强制终止 A。回收所有者持有租约时再次终止该进程，启动替代者或让健康副本接管，并放行旧执行者的迟到回调。含可核对效果与未知外部效果样本。
- 预期：单副本同时执行一条，两个就绪副本各执行一条不同 Run。控制落库后持租者停止派发并按安全边界确认释放。合法接管复用原 Run/Checkpoint，由有效回收者处理，旧 epoch 无新写入。未确认外部效果保留并阻止重放。其他健康槽可继续执行。
- 验证：记录排队、取消、最后心跳和回收时刻、真实 PID/boot ID/epoch、Checkpoint 与原/新 Attempt、独立效果计数、锁等待及其他 Run 连续进度。

### TC-28：跨副本 SSE、Redis 回退和状态投影

- 关联：AC-02、AC-08、AC-10、AC-11、AC-16、AC-19，评审 R9。
- 操作：从 A 订阅 SSE，持原游标切换至 B。分别在 Redis 追加成功与 SQL 投影确认之间中断发布者，恢复后放行旧发布者，并在独立样本注入去重索引缺失、流裁剪或 Redis 回退。使用高频公开增量夹具记录发布与队列等待。关闭外部观测出口，仍通过授权入口读取历史、Run Timeline 与状态。
- 预期：存在完整持久依据时续流保持包顺序和去重，失效的发布世代不能推进状态。需要安全重载或活跃流受阻时，客户端收到可判定状态并加载可用 SQL Message。显示、触发历史和诊断均沿用当前权限，遥测出口异常期间可读取已落库结果。
- 验证：比较完整 SSE/Message、Outbox 序、投影游标、包 ID 与发布世代。记录客户端状态、日志脱敏、锁等待与事件延迟。

### TC-29：候选迁移、两种角色部署与安全回退

- 关联：AC-09、AC-17、AC-19，评审 R11、R12。
- 操作：用 `agent/main` 空库及带旧会话、Run、Checkpoint、Action、待发布 Outbox 的 0014 数据运行迁移与派生 SQL 校验。按正式流程排空旧消费者、核对写入屏障，再启两个 Agent 和一个 Scheduler。试图误启旧 Agent/Worker 或第二个 Scheduler。保留定时受理和在途事件后回退，再恢复新版。
- 预期：空库、旧库、权限及迁移产物符合项目约定。旧执行或发布进程无法与新角色同时推进共享状态，重复 Scheduler 无写权。回退完整保留可核对的历史、触发关联、Checkpoint 和游标。读状态、继续执行和升级后的展示行为可用，待核对效果保持受阻。
- 验证：真实部署、就绪/失败日志、角色权限矩阵、实际写入计数、回退前后受理与已发布事件的对照。保留隔离源库、Redis 和密钥。

### TC-30：触发状态可查与观测归因

- 关联：AC-08、AC-14、AC-16，评审 R10、R12。
- 操作：分别制造未到期、已扫描待提交、429 退避、停止后补交付、Run 排队/运行/终止等记录。在 Run 完成后、Scheduler 状态回写前中断 Scheduler，再恢复。按计划、触发、请求、Run 和 Attempt 跨界面与日志核对。
- 预期：用户可区分是否完成交付、何时重试、是否进入 Agent 队列及实际执行状态，状态同步恢复后无倒退。授权诊断能关联 ID 与时序，公开结果省略内部凭据、原始工具载荷和其他租户数据。
- 验证：保存触发延迟、重试次数与原因、最老待交付、状态同步滞后及 Run 的排队/恢复时长。与运行配置和观测窗口一同记录，缺证据的场景标记未执行或受阻。

### TC-31：计划所有者授权贯穿查询、批准和恢复

- 关联：AC-12、AC-15、AC-19、AC-20，评审 R13。
- 操作：普通用户在副本 A 发起计划写入，在副本 B 查询待确认及 `allowedActions` 并批准。终止原 boot，让新 boot 接续，分别测试归属人仍有权限、批准后撤权、同工作区其他人及跨租户用户访问。另用普通成员和管理员分别尝试原业务审批，并用伪造请求字段尝试把业务审批改成计划确认。
- 预期：GET、动作提交和恢复派发均按持久提案种类及当前身份授权。普通所有者的授权计划可跨 boot 完成。撤权、身份不符或伪造提案种类无写入。前端区分已批准与计划已变更，原业务审批仍按管理员权限。
- 验证：记录受控账号权限、Actor、提案类型、两个 boot、Wait/Action 与持久效果。对照 Web/Chat 展示、HTTP 授权结果和实际写入计数。

### TC-32：同库计划效果与 Journal 接续原子性

- 关联：AC-05、AC-06、AC-12、AC-15、AC-19、AC-20，评审 R14。
- 操作：以受控 Chat 批准动作分别在工具派发后本地事务前、本地事务尝试写计划后但提交前、本地事务提交含 Checkpoint 后且外层未得到响应三个屏障中断执行进程。由新副本接续，重放同一 Action 或命令并核对 Resume、取消竞争与旧 epoch 的迟到回调。
- 预期：事务未提交时无部分效果，可由合法新执行权继续。在提交前观察不到单独已写的计划；提交后计划、命令、Action、规范化已接受 Attempt/工具输出和 Checkpoint 一起可见。外层 Journal 不覆盖原回执，恢复继续原 Run、复用已接受输出，计划版本仅增加一次。
- 验证：按数据库快照核对提交边界、Run/Action/Attempt ID、版本、输入摘要和 Checkpoint，再从 Chat 核对收到的结果及有无停留在未完成 Attempt。

### TC-33：交付状态机、最终时钟裁决和独立核对

- 关联：AC-05、AC-13～AC-16、AC-19，评审 R15。
- 操作：旧 Scheduler 开始交付后停在最后一个准入/触发锁前，令角色租约或触发令牌到期，再释放锁。交接到新世代，分别令旧世代未到期令牌和当前世代过期令牌进入可重领范围。在单独样本注入 202、429、403、暂态 5xx、超时及旧令牌 409。推进到次数或时间预算耗尽，使提交结果仍未知，并在仅核对入口返回前丢弃回执。检查普通交付选取和到期核对选取。
- 预期：取得所需锁后用数据库当前时钟裁决，过期或旧世代 409 停止旧尝试且无新接单。按失效原因重领并核对原记录。202 归入已受理，403 等确定性拒绝按契约收口，429/5xx/超时按契约重试，429 等待取 `max(Retry-After, 指数退避 + 抖动)`。耗尽后未知记录进入 `reconcile_pending`。仅核对入口可重试读取原接单和安全结算，无法创建新 Run 或绕过交付预算。已接单和明确未接单分别收口，仍未知继续待核对。
- 验证：保留数据库锁/时间屏障、角色世代和触发令牌、各响应的前后状态、计算后重试时间及耗尽后的入口调用计数。状态覆盖 `pending`、`dispatching`、`retry_wait`、`reconcile_pending`、`submitted`、失败和跳过。

### TC-34：默认容量、租户覆盖硬上限和有界领取

- 关联：AC-07、AC-14、AC-18、AC-21，评审 R12、R17。
- 前提：标准配置集群/租户在途为 1000/200，集群/租户积压为 3000/20。用隔离 PostgreSQL 预置符合约束的合成 job 建立积压，在边界仅通过真实受理链路新建少量 Run。可控执行样本单独验证在途，避免为规模样本批量调用模型。
- 操作：构造单租户 19/20、集群 2999/3000 的前后两侧，现有 job 状态组合按设计计数。分别用即时请求和到期记录在边界竞争并重放已受理请求。在集群仍有容量时使租户 A 饱和，测试 B 的提交及实际领取。校验低于和等于 20 的覆盖，并尝试高于 20 的覆盖。用合成已领取 job 配合真实领取验证集群 999/1000 和租户 199/200 的边界。租户执行槽边界单独以合成状态验证，通常先受积压 20 限制。对大积压、热点租户和不合格候选测量领取查询与准入锁。
- 预期：恰好触及限制的合法申请可接单，越界新请求得到 429 且无额外 Run/job/Outbox，原回执的受信重读遵守幂等契约。覆盖不能把租户积压上限放宽至 20 以上。只到租户上限时有集群余量的其他租户可接单及公平领取，领取批次遵守有界候选选择。即时和定时使用同一计数，在途两级上限均成立。
- 验证：登记合成 job 的分布与来源、两类回执、实际在途峰值、候选批次返回数、查询计划及准入锁等待，和小积压基线比较。指标目标以定稿参数为准。

### TC-35：工具声明容量、提案准备和批准后的串行派发

- 关联：AC-03、AC-12、AC-15、AC-19、AC-20，评审 R16。
- 操作：分别在 16 个声明和 64 KiB 边界配置计划工具、既有必需工具、工作流与可选 MCP。使用支持工具调用的模型夹具捕获实际发送的判别联合 Schema，再用能力不匹配的模型核对可见反馈。对已有 Run 在变更目录后从其他副本恢复。开启全局 parallel，覆盖计划查询、异步准备写提案、同批提出多项写入和批准后的恢复派发。保留原同步提案工具回归。
- 预期：固定容量为计划读写及必需声明预留空间，按规定稳定选择和记录被跳过的可选项。模型声明、执行注册及原 Run 冻结快照一致。批准前使用准备好的提案预览，恢复执行沿用持久批准内容。全局 parallel 下获批 `schedule_write` 仍单次独立串行，原确认规则、白名单和既有工具保持有效。
- 验证：对照实际 Provider 负载、声明数、序列化大小、目录指纹及被跳过项。在真实派发日志核对工具顺序、重复准备/调用计数、允许动作及最终计划效果。

### TC-36：副本配置校验与跨 epoch 记账

- 关联：AC-04～AC-09、AC-18、AC-19，评审 R17。
- 操作：让 B 分别用不同集群或租户容量、预算档案、关键依赖配置以及允许独立调整的本地槽/本地上游额度启动。使用配置一致的副本执行预算接近上限的 Run，在有已提交步骤、工具调用或物理 Attempt 后强杀 A，并在回收期间二次中断。保留长时间在途后费用仍未知的尾段，放行旧 epoch 回调。
- 预期：共享策略指纹失配的副本不具备接单/领取资格，允许独立的本地项保持可配置。接续从持久 Run 策略和消耗恢复，已结算耗时、步骤、工具和物理尝试不重复计数，崩溃尾段按定稿保守记账，未知费用和占用不意外归零。迟到写入被拒绝，余量不足时按同一预算收口。
- 验证：记录指纹和 readiness、两 epoch 的累计/未知计数、配额释放时点、独立上游请求计数及呈现的诊断结果。

### TC-37：保存检查、交付状态和执行失败提示

- 关联：AC-02、AC-12、AC-14、AC-16、AC-19、AC-21，评审 R18。
- 操作：Web 保存或预览时测试固定/自动模型可见性、工具能力、配置和权限。保存后停用模型或数据连接，触发含失配预算档案、Agent 429 后恢复、已受理但 Runtime 失败、等待确认或待核对等样本。在 Chat 和执行历史比较回执，断开 SSE 后重载。
- 预期：当前可提前确认的能力或权限问题给出可修复原因。保存成功只表示计划持久化，202 只表示该次触发已交付。按稳定阶段、原因、可重试标识及用户动作区分未交付、已交付后执行失败、等待和待核对。已受理关联保留；重载后状态与原因一致，敏感上游细节仅授权诊断可见。
- 验证：记录保存/预览结果、触发与 Run 回执、用户可见动作和安全原因码，复核诊断权限和坏依赖恢复后的行为。

### TC-38：发布入口、契约与 Worker 全量移除

- 关联：AC-09、AC-17、AC-19，评审 R11、R12。
- 操作：按定稿核对仓库入口、锁文件、生成契约、Compose、CI 和 manifest。后续在新旧共同数据的隔离发布演练中运行根 start/deploy/status/logs/down、CI 与部署 smoke，启动 Agent/Scheduler 两角色并分别处理即时与定时 Run。用旧 Worker 凭据、进程和旧领取/心跳/推进入口尝试在切换后写入，验证留存 Session/Run、Outbox、SSE 游标和回退再上线。
- 预期：新标准环境仅需同 App 的两角色，无独立 Worker 成员、服务、镜像、入口、凭据或运行等待。脚本和 CI 故障收集按角色定位。旧 Worker 写入从切换屏障起被拒绝，最终契约保留对外 Run/SSE/历史兼容行为。历史文档中的旧入口属于执行记录；迁移或回退说明可追溯到兼容版本。
- 验证：对照针对性的源码扫描、派生契约检查与实际启动调用图。记录新旧角色 readiness、路由/命令结果、镜像引用、有效写入计数和跨发布前后的 SSE/Message/Checkpoint 对照。

## 待验业务用例

### TC-01：无 Worker 受理与同键重试

- 关联需求：AC-01、AC-07。
- 前提与数据：两个 Worker 均未消费，A 有积压容量；新 Session 和已有空闲 Session 各一份。
- 操作：从真实 BFF 提交后关闭连接，查询原 Run；并发重复相同 requestId/输入，再用相同键改变输入。填满 A 积压后重试先前成功请求，再提交新请求。
- 预期：受理 202 后已有唯一 Session/Run/消息/初始投影/命令/job，公开 queued；没有模型或工具物理调用。相同输入取得原回执，冲突 409；满额旧回执仍可读取，新请求 429 且不产生 Run。启动 Worker 后领取原 Run 并完成。
- 验证：真实 HTTP、只读 SQL/用量、进程外物理调用数；记录受理与首次领取时间。

### TC-02：持久接收至首次派发窗口中断

- 关联需求：AC-01、AC-05。
- 前提与数据：真实受理事务提交后、首次交付前有屏障；受理前故障有独立反例。
- 操作：在提交后终止 Agent，保存原 requestId；恢复同库/Redis 与双 Worker；重发原请求。另对提交前中断重试。
- 预期：提交后的同一 Run/job 可补交付，只有一个用户命令回执；提交前事务整体回滚且重试可正常受理。Outbox、关键投影达到就绪后才派发，事件和最终答案可加载。
- 验证：实际进程记录、持久对象数量、调用数、HTTP 回执与同 Run Message。

### TC-03：所有接续入口遵循准入

- 关联需求：AC-01、AC-03、AC-07。
- 前提与数据：新 M6 parked Run；另从 0009 准备无 job 的 created/paused/waiting Run；A 执行槽或积压满额。
- 操作：分别使用 Resume、批准、外部事件及 v1 适配器；对满额旧 Run 先拒绝再释放容量后复用原 requestId 重试；对 M6 parked Run 在本租户积压已满时恢复。
- 预期：全部可执行入口只置 ready，未被 claim 时保持原可恢复状态和 queued 提示，不自行授予 epoch。新 M6 parked job 保留积压位置；旧无 job 的新增占位满额返回 429，原状态、未消费决定和请求键可重试。v1 共用配额，保留其断线取消约定；Web v2 离开页面后继续执行。
- 验证：各入口真实 HTTP、job/Run/Wait/命令差分及调用审计。

### TC-04：人工等待释放执行槽、批准一次

- 关联需求：AC-03、AC-07。
- 前提与数据：A 并发 1，广告预算审批 Run，A 另一就绪任务和 B 正常任务；原结果/文件已提交。
- 操作：首 Run 到达等待，检查资源清理与容量；待第二任务领取后批准首 Run，同时重复回调；待容量释放后继续原 Run。
- 预期：资源确认后首 job parked、不占执行槽且保留积压；后续任务推进。批准产生一个有效决定，原 Run ready 后受配额约束领取，沿用原 Wait/Action 和分析结果，效果一次；原产物仍可下载。
- 验证：Timeline 领取/确认释放区间、usage、Wait/Action、进程外效果计数和真实页面。

### TC-05：claim 回执丢失与 Worker 身份隔离

- 关联需求：AC-04、AC-05。
- 前提与数据：两个真实 Worker，claim 已提交但响应被阻断。
- 操作：同 workerId/boot 重试 claim，再由同 workerId 不同 boot 请求；交换服务凭据、修改正文 workerId、使用 BFF 用户凭据访问内部接口；Worker 凭据尝试用户 API。
- 预期：原 boot 取得相同 grant/epoch，claim_count 不增加；其他 boot 等待旧占用清理。同配置槽最多一条 leased/reclaiming。身份来自凭据，互换/伪造请求拒绝；grant 仅含执行标识和边界，无用户输入、数据源或模型秘密。无任务 204 带可用重试提示。
- 验证：HTTP 回执/拒绝载荷、只读 job 与 claim_count、物理调用数。

### TC-06：advance 双窗口丢响应及旧回执读取

- 关联需求：AC-05、AC-08。
- 前提与数据：边界有持久屏障，工具/模型由独立审计计数。
- 操作：分别丢弃 advance 受理响应和边界提交响应；反复提交同 grant/expectedCheckpoint，包含续租后的 expiresAt；边界完成并释放后读取原命令，再尝试以旧 grant 推进下一边界。
- 预期：同 Run/epoch/checkpoint 对应一个命令、一段执行；running 轮询不新建 Attempt；expiresAt 更新不改变命令身份。结果/Checkpoint/调度/回执原子收口，旧已提交回执只对原身份可读，旧 grant 无后继推进权；HTTP 断开保留原任务。
- 验证：命令/Attempt 数、真实依赖调用、回执与 Checkpoint、原 SSE。

### TC-07：等锁跨 TTL、过期续租与旧回调

- 关联需求：AC-04、AC-05、AC-06。
- 前提与数据：课堂 heartbeat 3 秒、TTL 15 秒；可控行锁和旧 delta 回调屏障。
- 操作：让 heartbeat、advance/业务提交分别等待行锁，锁在租约过期后释放；再用旧 grant 心跳和提交。新 epoch 建立后放行旧结果与 delta；另持续正常心跳记录控制版本。
- 预期：所有执行权检查采用取得锁后的数据库当前时间，过期返回 lease_lost。心跳仅改 expiresAt，不增加 Run.version、Outbox 或 Timeline。旧 epoch 无新业务提交、Checkpoint/成功消息覆盖或公开增量；已合法提交的旧 Outbox 可补发。补记原 Attempt 结局/费用保持其限定语义。
- 验证：数据库时刻、锁等待屏障、HTTP 结果、版本/Outbox 差分和完整消息；记录零迟到推进。

### TC-08：真实 Worker 终止与跨进程接管

- 关联需求：AC-04、AC-09。
- 前提与数据：Worker 1 已持久提交一个真实分析步骤；Worker 2 独立 PID/凭据/boot 可消费。至少包括普通分析与已有可核对动作效果两个场景。

- 预期：同一 Run/Action 保持；Worker 2 从有效 Checkpoint 继续，已完成分析与效果复用。Timeline 记录原领取、失效、确认释放/重新就绪及新领取原因；新 epoch 只在清理完成后建立，迟到推进零次，业务效果总数一次。
- 验证：PID 退出、两份 grant、Checkpoint/Attempt/Action、真实效果账本、最终 Message；受控可恢复夹具接管目标 ≤21 秒，按第 3 节设计实际计时。

### TC-09：执行超时与未知远端效果

- 关联需求：AC-05、AC-07、AC-09。

- 预期：超时有安全原因与原 Attempt 结局，重试只按既有策略产生新 Attempt 并保持预算。未知效果不自动重复物理调用，保守费用/资源占额保留；resources 未确认时 reclaiming 继续占槽，其他有剩余容量的租户可推进。明确暂停、未决审批与核对受阻的状态不自动续跑。

### TC-10：取消与动作发起、批准及接管竞争

### TC-11：正常退出与 Agent 启动恢复

## 度量与结果记录口径

- 接管成功率：需故障接管的全部 Run 为分母，已从合法持久位置完成接续为分子；未知效果、清理受阻单列并保留在总数中。另列无未决效果的受控可恢复子集，目标全部成功。
- 接管延迟：最后确认心跳停止至新合法 claim；记录清理区间、TTL、监督/轮询配置和实际最大值。课堂固定清理上界 2 秒时目标 ≤21 秒，超出直接记录目标未达成。
- 排队时延：Run.created_at 到 job.first_claimed_at，按租户报告样本数、p50/p95/max；空闲槽且无故障 B 样本目标 ≤3 秒。尚未领取的 Run 单列，不丢弃。
- 资源利用率：领取至确认释放区间在观察窗口内的累计时长 ÷（观察窗口 × 有效容量），清理隔离占用单独列出；跨窗口区间按窗口裁切。配额审计计入 leased 与 reclaiming。
- 成本：已结算 token/成本与未知保守占额分别列出；未知成本保留 null。效果只按稳定 Action ID 与进程外受控效果账本计数，费用和效果分别统计。
- 每次执行登记时间、源码/未提交范围、实际命令与 cwd、环境身份、退出码、Run/Session/Action 和观察结果。失败与修复后复验保留各自记录；文档格式检查仅记录在规划交付中。
