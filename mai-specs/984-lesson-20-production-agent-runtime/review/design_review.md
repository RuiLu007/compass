## 实施前发现

### R13 · P0 · 计划所有者授权还要贯穿恢复执行

方案已要求待确认查询和决策接口按持久提案种类分别授权。当前执行恢复又从已批准 Wait 读取确认人，在开始运行前直接以 `approval=True` 调用 Web 授权，而该分支仍要求租户管理员。只改查询、确认和工具本身时，普通用户可能看到「已批准」，随后恢复被 403 拒绝，计划一直没有写入。

**补齐**　让查询可执行动作、确认提交和恢复派发使用同一种持久提案判定。确认人、计划归属和执行前权限均按该种类核验，确认已提交与计划变更成功分开显示。测试普通用户批准后换副本恢复、批准后撤权、管理员业务审批回归及不同租户访问。[现行工具契约](../design/CODE_DESIGN.md#内置定时任务工具契约) · [恢复入口](../../../apps/agent/src/compass_agent/runtime/durable_service.py#L443) · [Web 授权](../../../apps/web/src/server/composition.ts#L144)

### R14 · P0 · 计划效果已提交时，现有 Journal 仍可能停止恢复

设计让计划、命令与 Action 效果在同库原子提交。当前工具外层 Journal 在派发前把 Attempt 持久化为 dispatched、Action 标为 unknown，绑定返回后才持久化工具输出、Checkpoint 并更新 Action。若进程在计划事务提交后、Journal.accept 前崩溃，当前复用路径先遇到未完成 Attempt 并返回 `execution_unknown`，可能到不了工具绑定中的原回执读取。外层更新也可能覆盖内部效果回执。

**补齐**　确定同库效果与 Journal 的唯一回执边界。优先让本地计划效果和可重放的 Attempt 输出一并提交；或在恢复、回收和再次派发之前加入仅适用于计划操作的回执核对，按 Action ID 与原输入摘要补齐 Attempt/Checkpoint。明确外层不得覆盖已提交业务回执。测试派发后写入前、写入后 Checkpoint 前、Checkpoint 后响应丢失三个故障屏障；期望未写可安全处理，已写可继续，计划版本只增加一次。[计划事务](../design/CODE_DESIGN.md#2-web-与-chat-计划写入) · [Journal 派发和确认](../../../apps/agent/src/compass_agent/runtime/journal.py#L584) · [未完成尝试的恢复](../../../apps/agent/src/compass_agent/runtime/journal.py#L475) · [当前回收](../../../apps/agent/src/compass_agent/runtime/run_scheduler.py#L570)

### R15 · P1 · Scheduler UML 缺少令牌和核对路径的完整契约

扫描、交付、状态同步和角色租约已经分开。ER 图和 UML 仍缺少交付令牌绑定的持久 Scheduler 世代或等价关联、接管后的重领条件，以及预算耗尽后的核对入口。代码片段先校验角色租约，再等准入锁和触发行锁。如果实现照此顺序取时钟，等待期间过期的角色租约可能被当成有效。又如第八次失败后，普通交付领取可能不再选中该记录，但当前没有明确一个选择到期未核对记录的查询或状态转换。

**补齐**　列出状态转换表，覆盖 pending、dispatching、retry_wait、待核对、submitted、failed、skipped。补清三项：世代和令牌在主库如何存及失效，取得锁后何处用数据库时间做最终校验，到期核对如何被有界选取并最终收口。明确 HTTP 202、429、403、暂态 5xx、超时及旧令牌 409 的映射，旧令牌错误只停止该次尝试，重领后仍可核对原回执。当前 Agent 429 的 Retry-After 为 1 秒，应作为退避下限使用，避免短时间耗尽 8 次交付预算。可沿用现有两个循环，明确其查询分支即可。加原 Scheduler 等锁跨 TTL、重启时已有交付令牌和核对响应丢失用例。[交付契约](../design/TECH_DESIGN.md#到期与交付合同) · [受理伪代码](../design/CODE_DESIGN.md#3-到期http-交付与受理)

### R16 · P1 · 自然语言工具尚缺目录容量和并行模式规则

两工具的类型、范围和审批主体已经明确。当前工具目录最多 16 个声明、合计 64 KiB。新增两个默认工具可能挤掉现有工作流或 MCP，超限时会直接停止工具装配。另一个可复现问题是方案明确写工具 `parallel_safe=False`，当前批次预检在配置为 parallel 时会拒绝此类工具。用户确认后，恢复的写调用也可能被拒绝。

**补齐**　为两个内建工具明确目录优先级和配额，冻结目录时记录被跳过的可选项；已有 Run 恢复维持原快照语义。为确认型写操作定下单独串行派发规则，覆盖全局 parallel 下确认前后及同批多写请求。验证厂商收到的判别联合 Schema 支持工具调用，模型声明和实际注册使用同一快照。为 AC-12 加满目录、parallel 配置和具备/不具备工具调用能力的模型。[工具注册设计](../design/CODE_DESIGN.md#内置定时任务工具契约) · [目录限制](../../../apps/agent/src/compass_agent/tools/registry.py#L91) · [批次预检](../../../apps/agent/src/compass_agent/tools/batch.py#L39)

### R17 · P1 · 多副本必须统一运行策略并明确跨世代记账

方案给出了每 Run 租约、控制意图、回收令牌和跨副本续流。当前创建 Run 的私有快照记录执行时限和输入，模型预算档案和上限仍由当前进程装配。A 与 B 若配置不一致，B 可能用不同上限恢复同一 Run，或因模型档案失配暂停。当前已确认步骤会保存耗时和用量，未完成步骤在强杀时还存在尾段时间、未知费用和占用的结算窗口。

**补齐**　定义共享策略版本或等价配置指纹，Agent 副本就绪时核对全局/租户准入、预算档案与共同依赖配置。本地槽数和实例分配的上游额度可以独立配置。定义跨 epoch 的耗时、步骤、工具和物理尝试记账权威源及未知费用处理。可按步骤和物理 Attempt 恢复，明确崩溃尾段的保守记账。验收以策略漂移、剩余预算紧张时接管、原执行者迟到和回收者再次中断为夹具。[多副本共享状态](../design/TECH_DESIGN.md#41-多副本共享状态) · [Run 快照](../../../apps/agent/src/compass_agent/runtime/store.py#L378) · [当前 Runtime 装配](../../../apps/agent/src/compass_agent/api/runs.py#L155)

### R18 · P1 · 定时计划可保存与可运行需要分别反馈

计划输入支持固定或自动模型，真正模型筛选、分类路由、预算档案和工具装配都发生在 Run 后续阶段。普通 Chat 的计划请求同样要先跑一次模型。当前方案把权限和 Cron 校验写清楚了，但 Web 历史和 Chat 回执还缺少「未交付」「已交付后执行失败」「等待确认或待核对」的统一原因与恢复办法。一次 202 只能证明已有 Run，计划保存也不能承诺未来配置不变。

**补齐**　在 Web 保存或预览时检查可提前确认的模型可见性、能力、配置和权限，返回可修复原因；到期交付和执行仍按当时权限和 Provider 状态重验。执行历史保留失败阶段、稳定原因码、是否可重试及对应用户动作，敏感上游细节只进授权诊断。覆盖模型/数据连接在保存后被停用、预算档案失配、队列满后恢复、Runtime 失败后原触发仍显示已受理、SSE 断线重载。[计划管理](../design/TECH_DESIGN.md#2-定时任务增删改查) · [现有 Web 错误归类](../../../apps/web/src/server/http/durable-analysis-handler.ts#L166) · [失败配置盘点](runtime-failure-config.md)

## P0 · 实施前修正

### R5 · Chat 计划审批沿用了管理员入口

PRD AC-12 面向普通经营分析员。设计要求复用原 HITL，但当前 Web 运行授权在 `approval=true` 时要求租户管理员，普通创建人无法确认自己的计划。现有回调的 purpose 只有 `chat/runtime_usage/runtime_diagnostics`，Chat 与定时触发也没有明确怎样校验 `module.automations`。直接沿用可能出现 Web 拒绝而 Chat 可以改，或计划权限撤销后仍能触发。

**修正**　明确 Web、Chat、API 和后台触发的授权矩阵。计划写确认使用按提案种类绑定的「计划所有者确认」，保留现有分析动作的管理员审批规则。需要在读取、提案确认和实际写入复核当前权限。需求负责人明确撤销 `module.automations` 后现有计划是否继续运行，并将同一规则写进触发校验。AC-12/14 增加普通成员、同租户其他用户、被撤权用户和服务调用四类用例。[需求](../spec/PRD.md#自然语言对话) · [现有审批规则](../../../apps/web/src/server/composition.ts#L144) · [授权回调](../../../apps/web/src/app/api/internal/analysis/authorize/route.ts#L9)

### R6 · 计划写入缺少批准、取消和接管的事务边界

现有设计附录的 `mutate_plan` 事务只校验计划版本和命令键。批准后旧执行者可能在取消或租约失效之后才拿到计划行锁。Action ID 去重能让同一批准只写一次，首次写入仍需要当前执行权裁决。现有工具的 `approval` 是工具级策略，单一 `schedule` 工具还需要明确怎样让读取直接通过、写入走审批。

**修正**　Chat 写入在 Agent 同库事务锁定 Session、Run 与 Action，校验租约、epoch、取消及批准快照，再锁计划并原子写计划和效果回执，明确命令键与计划锁顺序。重放已提交效果只读取原回执。Web/API 直接写通用计划服务，按调用者身份授权。工具读写分支可用明确的操作级审批接缝，或拆为读工具和写工具，保留自然语言的四种能力。并发验收批准与取消、Web 改版、旧副本迟到、事务提交后故障。预期只有有效执行者可首次写入，同一已提交效果可重读。[设计伪代码](../design/CODE_DESIGN.md#2-计划写入和到期扫描) · [现有工具准入](../../../apps/agent/src/compass_agent/tools/dispatcher.py#L156)

## P1 · 影响上线与验收

### R7 · 跨副本暂停与取消缺少可执行的控制路径

主方案要求持租副本正常收口，当前恢复循环却扫描所有暂停请求，并根据本地 `tasks` 缺失强制撤权。迁回循环时如果漏改这条路径，B 收到暂停或开始维护就可能撤销 A 的有效租约。取消在另一个副本被受理后，也需要一个确定的时点通知持租者。

**修正**　把「用户请求落库 → 持租者观察意图 → 停派发与确认释放 → 过期接管」展开成状态转换。持租者在有界控制轮询和步骤派发前读取意图；回收者只走合法过期回收。把续租或等待竞争、跨副本调用 B 取消 A 执行、重启 B 保留 A 租约列入 AC-04/06/19。[设计](../design/TECH_DESIGN.md#41-多副本共享状态) · [现有恢复循环](../../../apps/agent/src/compass_agent/runtime/durable_service.py#L304)

### R8 · 同库交付可以少一个故障窗口

计划交付和 Run 受理归同一个数据库。当前方案先提交 Run，再用下一笔事务关联触发。期间 `run_id` 为空，进程中断会让计划继续占用不重叠位置。现有用户 submit 的旧回执读取会经过 Session 可见性，用户若先删除已完成的会话，后台必须仍能识别已受理的 Run，避免履历挂起。

**修正**　优先把触发的 `run_id/submitted/accepted_at` 放进已有受理事务，在取得准入锁、命令键和触发行锁后一次提交。保留稳定 requestId、领取令牌和单独同步运行结果。若保留两笔事务，明确内部回执查询绕开用户展示过滤且只接受同触发归属、摘要和 kind。增加「已受理、会话软删、恢复关联」用例。[受理与关联时序](../design/TECH_DESIGN.md#3-状态持久化和到期交付) · [现有受理回执读取](../../../apps/agent/src/compass_agent/runtime/store.py#L312)

### R9 · 跨实例事件发布缺少 Stream 代际与保留合同

方案已有每 Run 的发布世代、包级去重和 SQL 投影条件提交。仍需明确 Redis 去重索引、发布世代键与 Stream 的保留关系，及 Redis 数据回退、缺失或部分发布后如何处置。当前校验遇到活跃流缺失会阻塞或安全重载，历史已投影 Outbox 会被标为已投递。开启多实例后若直接在缺失 Stream 上重建去重索引，旧游标和包顺序会失去依据。

**修正**　明确只允许单调发布世代、原子去重键与 Stream 的共同生命周期。明确活跃流丢失继续安全阻断或按规定重载，用户提示须与 PRD AC-19 对齐。验证 Redis 追加后 SQL 未确认、旧发布者恢复、流裁剪和 Redis 回退。保留既有 SQL 快照和 Outbox，按可证明恢复能力设定验收。公开 delta 全部先入 SQL 后，还需要给出批次刷新节拍和内容上限，验证高频输出不会拖慢同库领取。[发布设计](../design/CODE_DESIGN.md#5-跨副本接管与发布) · [现有 Redis 校验](../../../apps/agent/src/compass_agent/runtime/redis_stream.py#L77)

### R10 · 交付重试与待处理计划缺少可操作的收口规则

方案定义了 429 退避、重试耗尽和同计划跳过，但还没有规定默认重试次数或交付截止，也没有明确长期 `paused`、未知外部效果，以及停用后某条已领取触发一直退避时用户如何处理。Run 积压限制发生在接单时，无法限制上游的启用计划或待交付触发量。

**修正**　给课堂档位配置并写明最大交付期限、Retry-After 的裁决、哪些原因可重试，以及积压达到上限后按租户怎样反馈和处理。历史显示下次重试时间、阻塞原因和相应原 Run 操作。明确停用/删除后的已领取交付会继续多久，说明排队、等待人工与暂停是否阻挡下次执行。曾受理而终态失败的 Run 是否支持手动重跑、怎样关联原触发也应明确。验收长时背压、撤权、计划停用、长时间暂停及另一个租户保持服务。[业务规则 BR-13～BR-15](../spec/PRD.md#6-业务规则与约束) · [调度与持久化](../design/TECH_DESIGN.md#3-状态持久化和到期交付)

### R11 · 旧、新执行与发布协议切换缺少强制隔离方式

方案要求两代协议不能同时写，但步骤仅描述先停旧进程再启新进程。误启动的旧 Agent 仍可能拿到旧 advisory lock，而新实例按 Run 授租；旧发布者还可能绕过 Redis 世代检查。回退同样需要明确旧构建怎样保留新版本期间已关联的 Run 和游标。

**修正**　给兼容构建设置互斥启动模式或版本就绪门禁。明确旧构建在新 schema 下的拒绝条件、旧凭据及活跃进程的关闭验收、发布游标兼容规则。两代模式切换需验证误启动旧版本、在途取消、未发布 Outbox 和 0015 保留数据回退。条件顺序先跑双副本只受理/领取及共享发布，再开启定时交付链。[迁移与回退](../design/TECH_DESIGN.md#6-数据迁移发布与实施任务)

### R12 · 现有业务验收计划仍停留在双 Worker 基线

新 PRD 已覆盖 AC-12～AC-19，但测试计划仍以一个 Agent 和两个 Worker 为拓扑，现有通过记录只覆盖这一基线。当前“并行数增加”应在两租户、同集群配额、同依赖容量下可重复验证。

**修正**　补一组明确的真库、双 Agent 和浏览器用例。用受控长步骤观测单副本同时 1 条、双副本同时 2 条有效 Run；并发启动、运行中终止执行者、终止回收者、旧 epoch 迟到、跨副本查状态和续流分别核对。记录触发/交付/排队/故障接续时间及锁等待。Web 与 Chat 各自完成完整 CRUD，并跨入口改同一记录、行使过期版本和撤权场景。保留旧用例的可迁移断言。[历史测试计划](../test/TEST_PLAN.md#范围与依据) · [新验收标准](../spec/PRD.md#ac-18多实例并行执行与扩容)

## 可在修订时一并收敛

## 必须修正项

### R1 · P1：接口、事件存储与前置生命周期已过期

原主方案第 3 节使用 durable-runs、SQL agent_event.seq、run.succeeded.finalAnswer，文件清单还引用 durable_store、durable_executor 等旧模块。M5 当前有效设计已采用 sessions/submit、Message JSON、Run SSE、AgentResponse v2、Redis Stream ID 和 SQL 完整投影，并已负责 202 接单与连接解耦。

**影响：** 按原文实施会形成两套流、状态包及投影逻辑，刷新与续流无法共用 reducer；重复建设 M5 接单能力。

**已修正：** 主方案“需求依据与验收”、第 1/3/5 节及代码附录第 5 节统一引用 M5 当前合同。完整答案使用同一成功批次的 completed message/run upsert，v1 沿用适配器。短期流过期回到 Message，活跃流丢失保留恢复受阻；调度 Timeline 进入完整投影，运维内部字段单独授权读取。阅读版采用同一源图和代码引用。

**后续验证：** AC-02、AC-08、AC-10、AC-11；刷新、终态流过期、受限字段、权限变化、旧事件重复与手动展开。

### R2 · P1：调度锁顺序遗漏 Session，接续入口可能绕过队列

原文和伪代码从 Run/job 起锁；M5 的提交、HITL、Checkpoint 使用 Session→Run。原方案只概述批准后重新入队，未明确替换 M5 中 submit/Resume/decision 的直接任务启动。

**触发与影响：** 领取或结果提交持有 Run 后进入 M5 的 Session 写入，与已持 Session 的控制事务形成相反等待顺序；如果保留旧直接启动，审批、恢复或 v1 入口可以绕过租户容量。

**已修正：** 主方案第 2 节与代码附录第 2～4 节统一调度锁（需要时）→Session→Run→job→Step/Attempt→Wait/Action。控制事务不反向取调度锁；可能给遗留 Run 补 job 的控制从事务起点取得准入锁。所有可执行入口只入队，claim 唯一授予 epoch；实际执行保持 Agent 单所有者。

**后续验证：** AC-01、AC-03、AC-06、AC-07；控制/领取/提交交错、既有 Waiting/Created 无 job、满额时决定保持可重试、v1 与新入口共用配额。

### R3 · P1：租约与推进回执缺少必要失败分支

原代码只展示领取和最终提交，未展开 heartbeat、claim 响应丢失、advance 在途重发及 Agent 重新启动时的裁决。原文提到“数据库时钟”，没有限定等锁后实际时钟。接管虽要求清理，但 Worker 身份、存量命令回执和旧流回调的落点仍不完整。

**触发与影响：** 响应丢失可让 Worker 漏领自身任务；失效心跳或在途重试可重复启动；以事务起始时间判断 TTL 会把等锁后的过期提交判为有效；只隔离最终结果会留下旧流回调污染新执行视图的窗口。

**已修正：** 代码附录第 1/3/4 节明确 credential→workerId、每进程 bootId、Run execution_epoch、稳定 advance 键、agent_command 内部回执及同命令轮询。取得行锁后用 clock_timestamp 判断 TTL；过期心跳拒绝。reclaiming 撤权且占槽，清理原执行、流回调和效果后才重新排队；Agent 重启先恢复持久底座并核对旧执行。release 只能请求边界释放，Worker 不能上传业务结果或自行清空占用。

**后续验证：** AC-04～AC-06；真实 Worker 退出、同命令重复投递、过期续租、等锁跨 TTL、旧回执重读、旧 delta 回调、Agent 重启、未知效果隔离和取消竞态。

### R4 · P1：用量读取与恢复验收缺少可执行落点

原文定义了统计口径，但未给租户用量查询入口，恢复阈值只写“Lease 窗口加清理/轮询延迟”。调度事件若直接依赖已被 M5 替换的 SQL event 表，Redis 到期后的 Timeline 也没有明确读取来源。

**影响：** FR-05/07/08 对用量、持续可读 Timeline 和恢复目标的验收难以逐项执行，课堂报告可能遗漏受阻任务。

**已修正：** 第 3 节登记当前授权租户的 runtime/usage 接口，从 job 与 M5 预算/Attempt 聚合；Timeline 复用完整 public_view，心跳不落逐次事件。固定双租户负载和受控夹具的 21 秒恢复、空闲容量下 3 秒领取设计目标，解释时间组成、阻塞分类和成本未知值。第 5 节登记故障矩阵、恢复报告及相应测试入口。

**后续验证：** AC-07～AC-09；各租户容量、超额返回、预算耗尽、当前权限、排队/恢复耗时、利用率及受阻分母。数值均为设计目标，本轮没有负载或恢复实测。
