## 第 1 页：LLM Application Runtime 的可观测范围

原图：[第 1 页](codex-clipboard-f37a195d-6c75-4022-beb8-ddf7acaa1a04.png)。

### 定义

通过采集、关联和分析模型调用执行过程中的信号，了解每一次 LLM 调用的执行状态、性能、成本、质量与异常，并在出现问题时快速定位根因。

### 分层与职责

| 层级                              | 内容与职责                                                                                           |
| --------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Agent Harness，任务级             | Run / Task / Step、任务成功率、工具调用；向下关联 Trace Context                                      |
| LLM Application Runtime，本课重点 | 调用生命周期；TTFT / Token 吞吐；流式输出状态；模型路由决策；重试 / 降级 / 熔断；Token / 成本 / 配额 |
| LiteLLM Core SDK                  | HTTP 请求、Provider 适配、SDK 异常、原始用量；承接 Provider 请求与响应                               |
| Inference Runtime / Provider      | GPU 利用率、KV Cache、推理队列、模型内部计算                                                         |

### 观测维度

可靠性、性能、流式执行、路由与 Provider、成本与资源、治理决策。

### 核心观测对象

一次逻辑模型调用（Logical LLM Call）覆盖路由、限流、实际请求、重试退避与最终结果，端到端逻辑调用耗时覆盖整个过程。

PPT 示例：路由 2 ms → 限流 1 ms → 请求①超时 → 重试退避 → 请求②成功。该流程为教学示例；具体错误是否允许重试由第 13 课的执行与恢复判据决定。

### 边界

- 向上：承接 Agent Harness 的任务级观测（Run / Task / Step）。
- 向下：依赖 SDK 与推理服务的请求级、资源级观测（HTTP / GPU 等）。

## 第 3 页：基于需求分型的决策方法

原图：[第 3 页](codex-clipboard-22409cd8-8318-4d66-8295-19c374f80474.png)。

### 判断输入

| 输入         | 考量                     |
| ------------ | ------------------------ |
| 行业属性     | 合规 / 安全 / 审计要求   |
| 业务场景     | 交互 / 数据分析 / 决策等 |
| 产品阶段     | MVP / 增长期 / 成熟期    |
| ToC / ToB    | 用户体验 / 租户治理      |
| 用户量级     | QPS / 在途调用 / 数据量  |
| 技术栈与架构 | 单体 / 微服务 / 异步任务 |
| 部署方式     | SaaS / 私有化 / 离线     |
| 团队能力     | 复用已有平台 / 自建运营  |

### 决策路径

1. 存在强制的数据驻留、审计或隔离要求：叠加 D 类合规隔离约束，可与 A / B / C 组合。
2. 存在大规模并发、跨服务执行或严格 SLO：选择 C 类规模治理型。
3. 在线上稳定运营，需要持续治理与分析：选择 B 类生产运营型。
4. 其余以 MVP、低流量和排障为主的场景：选择 A 类轻量诊断型。

### 类型与技术组合

| 类型                       | 需求重点                                                     | 建议技术组合                                              |
| -------------------------- | ------------------------------------------------------------ | --------------------------------------------------------- |
| A 类：轻量诊断型           | 基础调用日志与指标；延迟、成功率、用量统计；开发期排障与调试 | OTel Python SDK + LiteLLM 埋点 + 日志 / 指标后端          |
| B 类：生产运营型           | 调用追踪与故障诊断；SLO、告警与模型分析；按需接入评估与调试  | OTel + 现有 APM（如 Grafana），或 Langfuse、Phoenix       |
| C 类：规模治理型           | 全链路追踪与容量治理；采样策略与成本控制；SLO 与告警         | OTel + Collector + Metrics / Trace 后端 + 采样 / 队列治理 |
| D 类：合规隔离型，叠加约束 | 数据本地化与内容脱敏；权限隔离与审计记录；可私有化部署       | OTel + 本地存储 + 权控 / 审计                             |

### 选型结论的输出方式

- 基于行业、场景、阶段、规模、架构、部署与团队能力，按决策树判断 A / B / C，并结合合规要求叠加 D。
- 按需求类型选择 OTel、LiteLLM、Collector、APM 或 LLM 专用平台的组合，明确建设边界与增量条件。

## 第 4 页：DataAgent Compass 的选型与取舍

原图：[第 4 页](codex-clipboard-f86b2c4e-9243-4be9-b312-8f179eec09cd.png)。

### 项目画像

| 维度     | PPT 中的项目定位                               |
| -------- | ---------------------------------------------- |
| 产品类型 | ToB 企业级 Data Agent                          |
| 业务场景 | 多模型调用、流式输出、重试降级、超时取消       |
| 产品阶段 | 生产运营型（非 MVP，非大规模治理）             |
| 技术架构 | Python 进程内薄 Runtime，基于 LiteLLM Core SDK |
| 并发规模 | 尚未明确，预留高并发演进能力                   |
| 数据安全 | 可能涉及数据库 Schema、SQL、查询结果等敏感内容 |
| 团队能力 | 优先复用成熟组件，控制长期运维成本             |

该画像是选型输入；业务能力的交付状态以对应 Feature 记录为准。

### 关键选型考量

| 决策点     | 选择与理由                                            |
| ---------- | ----------------------------------------------------- |
| 观测标准   | 使用 OpenTelemetry，保证通用性与可迁移性              |
| 模型埋点   | 复用 LiteLLM 回调 + 少量自研适配，避免重复开发        |
| 观测粒度   | 采用 Logical Call + Attempt，区分重试、降级与实际调用 |
| 关键指标   | 成功率、延迟、TTFT、取消、重试、Token 与费用          |
| Trace 策略 | 初期轻量链路，按规模采样，控制存储成本                |
| 导出架构   | 进程内异步、有界导出，不影响模型调用                  |
| 内容采集   | 生产默认不采集 Prompt / SQL / 结果正文，降低数据风险  |
| 费用与审计 | 区分观测统计与正式计量账本，不依赖采样 Trace 做强审计 |

### 最终结论

选择 B 类“生产运营型”作为基线，采用轻量 OTel 埋点 + LiteLLM + 复用现有可观测平台的技术路线，并预留向 C 类“规模治理型”演进的能力。

### 推荐架构

1. Agent Harness：Run / Task / Step、租户与业务上下文。
2. Compass LLM Runtime（进程内）：统一模型调用执行与观测语义。
   - LiteLLM SDK：Provider 调用与回调。
   - OTel API / SDK：Trace、Metrics、Context。
   - Runtime 埋点适配：Logical Call / Attempt。
   - 隐私与数据策略：脱敏、采样、有界导出。
3. 现有 APM / Metrics / Trace 后端：优先复用已有平台；无现有平台时再选托管或自托管，例如 Grafana、Langfuse、Phoenix。

### 明确不做的事项

- 不部署独立 LLM Gateway / Proxy。
- 不自建通用可观测平台或 Trace 存储。
- 不在 Runtime 内建设 Prompt 管理、数据集和效果评估平台。
- 不默认引入 Kafka、复杂尾采样集群或独立 Collector。
- 不默认持久化完整 Prompt、SQL 和模型响应。
- 不把观测平台作为计费、配额和强审计的唯一事实来源。

### 升级条件与演进路径

| 升级条件                    | 演进措施                         |
| --------------------------- | -------------------------------- |
| 观测数据量与成本显著增长    | 采样、字段裁剪、分层留存         |
| 多服务 / 跨 Worker 链路复杂 | 引入 Collector，强化上下文传播   |
| 需要系统性比较模型与效果    | 引入 Langfuse / Phoenix 等平台   |
| 多租户需要独立查看观测数据  | 加强租户授权与存储隔离           |
| 客户私有化或强合规要求      | 本地观测后端、内容控制、独立审计 |
| 正式按模型用量收费          | 建设持久计量与供应商对账链路     |
