## 4. 兼容性与部署

| 边界             | 兼容规则                                                                              | 发布或恢复要求                                                            |
| ---------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Web → Agent HTTP | 公开 DTO、错误 envelope、事件名和空值语义保持一致；增加必填字段或新事件前明确版本策略 | 生成契约后执行 JSON/SSE 与浏览器回归，协调两端发布                        |
| Runtime 内部接口 | ExecutionRequest、RuntimeResult 与 ProviderAdapter 由 Agent 同步维护                  | 内部调用者随 Agent 一起更新；其他应用通过 HTTP 调用                       |
| 数据库           | Agent 拥有模型配置、变更与调用表；Web 拥有身份、租户与调用权限                        | 先供应角色并建立完整表结构，再启用模型入口；schema 管理账号与运行账号分离 |
| 凭据与续接       | Fernet 密文需要对应主密钥；续接绑定身份、作用域、模型绑定版本及 900 秒 TTL            | 主密钥与数据库分别备份；更新密钥须配套明确迁移，过期续接重新发起交互      |
| 回退             | 应用构建须兼容保留的 schema、HTTP 契约及密文格式                                      | 等待在途调用结束后切换构建；恢复数据库使用新受管库及原密钥，保留原库      |

**安装与发布顺序**

1. 准备 Node.js 24、Python 3.13、PostgreSQL 17、pnpm 与 uv，安装 Web 和 Agent 依赖。
2. 为 Web 与 Agent 分别设置供应、迁移、运行账号及数据库连接。供应账号创建数据库与角色，迁移账号管理 schema，运行账号仅持有业务所需权限。
3. 供应与迁移：`pnpm db:provision -F agent`、`pnpm db:provision -F web`，随后执行 `pnpm db:migrate -F agent`、`pnpm db:migrate -F web`。首次安装创建全部模型表和调用权限；已有数据库按版本顺序升级。
4. 设置 §2.2 中的服务令牌、Fernet 主密钥、供应商 HTTPS origin 与内部 Agent 地址。两端使用相同服务令牌；凭据仅保存在服务端。
5. 通过静态检查、契约检查、单元测试、PostgreSQL 集成与浏览器回归，执行 `pnpm build -F agent`、`pnpm build -F web`，发布应用。
6. 检查 `/healthz` 与 `/readyz`；平台管理员添加并测试模型，配置启用与 Chat 可见性，再为租户成员显式授予 `models.invoke`。用户需同时具备分析入口权限。
7. 使用有权限的租户账号验证选模、流式回复、停止和调用记录查询。升级时先备份数据库与主密钥，等待在途请求结束后重启；失败时保留实际版本与记录，按兼容构建恢复。

这些命令由 Compass 工程根目录提供。迁移在显式工具入口执行，应用启动与接口导入均不隐式改表。供应商账号需具备所选模型的实际权限；生产容量与供应商限流额度共同决定可开放的并发量。

## 5. 实施拆分与验证方法

| 实施单元       | 主要交付                                                 | 完成条件                                                                   |
| -------------- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| 模型配置与权限 | Provider、变更记录、加密凭据；平台管理入口与租户调用授权 | 配置可持久保存；幂等、乐观锁、端点限制和越权访问测试通过                   |
| 契约与能力     | 公开 DTO、内部请求/结果、错误类型及能力规则              | 生成与决策载荷语义清楚；不支持的能力在出站前拒绝；HTTP 与类型定义一致      |
| 适配器与传输   | 生成/决策适配器、流式归一、工具续接与有界读取            | 每调用最多一次物理请求；流终止、工具聚合、结构化输出、密文绑定验证通过     |
| 生命周期与记录 | Runtime 的时限/取消/资源收尾；应用服务的准备与元记录     | 首包前、流中、收尾和重复取消均有界退出；不误报成功；数据库写入失败明确反馈 |
| 产品链路       | 模型测试、Chat 选模、流式展示、停止与作用域切换          | 用户选择进入实际调用；迟到片段不污染页面；管理与租户边界正确               |
| 并发与性能     | §1.1 的受控上游压测、资源曲线和错误分类                  | 记录机器配置与负载口径，验证成功率和延迟目标；达到指标后确定可发布容量     |

**分层验证**

- **内核测试：** FakeAdapter 验证执行期限、成功/失败/取消、深拷贝、资源关闭和回压，无需数据库或真实供应商。
- **协议集成：** 可控 HTTP 上游覆盖同步/流式、工具/JSON、429/5xx、压缩体、断流和终止标记；同时核对物理请求次数。
- **数据库集成：** 使用专用 PostgreSQL 验证空库安装、升级、并发占位、配置快照、终态竞争、角色权限与恢复。
- **浏览器端到端：** 覆盖添加配置、能力测试、Chat 选模、停止、切换上下文、权限拒绝与错误展示，验证最终页面和记录。
- **供应商联调：** 使用获准的真实账号分别核对三款模型的协议与实际能力。阿里云决策模型已有受控协议验证，真实账号联调仍待完成。
- **容量测试：** 先验证受控上游下的本地运行开销和并发隔离，再测真实供应商限额。§1.1 的并发成功率与 P95 目标保留待压测状态。

工程检查入口包括 `pnpm lint -F agent`、`pnpm typecheck -F agent`、`pnpm test -F agent`、`pnpm test:integration -F agent` 和对应 Web 检查；HTTP 类型同步使用 `pnpm contracts` 与 `pnpm contracts:check`。跨应用集成后运行 `pnpm check`、`pnpm build`，部署联通性使用 `pnpm smoke`。

**扩展条件：** 自动模型选择需要引入候选解析和显式路由策略；重试与降级需要增加 Attempt、共享时限及用量聚合；完整观测需要定义 Trace、采样、脱敏和成本口径。新增能力同步更新契约、数据归属与测试，目录随实际代码创建。
