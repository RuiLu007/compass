## 需求简述

Compass 是电商经营分析 Agent。第 11 课建立统一的模型接入与单次执行能力，第 12 课在它前面增加两级意图分类、字典特征提取与模型选择，让用户通过同一个 Chat 入口获得适合当前任务的模型响应。

| 产品入口         | 用户操作                             | 系统行为与结果                                                               |
| ---------------- | ------------------------------------ | ---------------------------------------------------------------------------- |
| 分析 Chat        | 输入业务问题，选择自动或指定主模型   | 一轮发送一次请求；服务端完成分类、查表、选模与一次主模型推理                 |
| 路由详情         | 查看本次分类和模型选择               | 分别显示一级分类、二级场景、字典特征、实际模型、选模原因及分项用量           |
| 闲聊与范围外请求 | 提出日常闲聊或非业务任务，可预选 Pro | 命中 SC-39 后使用 Flash 与独立提示词，温和说明经营分析范围并询问业务数据任务 |
| 停止生成         | 在分类或推理阶段停止                 | 取消向当前调用传播，后续分类与推理停止，迟到片段退出当前页面显示             |

**贯穿样例：** 用户问“比较这份渠道汇总”，模型先返回 `category_id` 与 `scene_id`；字典查出任务类型、难度、响应方式和能力要求。自动模式按难度选择 Flash 或 Pro，固定模式使用用户指定主模型。若用户问“讲个故事”，系统按 SC-39 的独立规则使用 Flash，返回范围说明和业务任务引导。

本课聚焦分类到推理的最小闭环。真实取数、工具执行、Skill/subAgent/workflow 分派、多步计划及生成恢复由后续能力承接。本文为待实现设计；类型和核心算法包含伪代码，具体模型版本、字典字段与时间预算仍需接入确认。

## 1. 方案概述

### 1.1 设计目标和设计原则

#### 1.1.1 可检验的设计目标

O 描述目标，KR 描述可观察结果。当前验证重点为流程、契约和模型接入；效果调优、正式留出分类评测和分类准确率准入安排在后续课程。

| 目标 O               | 可检验结果 KR                                                                                                   |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| 分类输出简单且可校验 | 业务输出严格包含两个 ID；多余字段、未知候选和父子归属错误被拒绝                                                 |
| 特征和路由可预测     | 特征全部来自当前字典快照；业务 L1 → Flash，L2/L3 → Pro；固定选择按用户指定模型执行；SC-39 优先走 Flash 专用响应 |
| 前端使用统一推理入口 | 每轮只请求一次 models/calls；同步与流式最终响应均保留 intent/features/routing/result/metrics                    |
| 控制模型调用次数     | 正常路径至多一次 JEV 分类与一次主模型推理；兜底路径至多一次 JEV、一次 Flash 分类和一次主模型推理                |
| 失败与停止有明确结果 | 两路分类失败时主模型调用为零；取消、撤权和父时限耗尽后停止出站；主模型失败按已有 Runtime 结果结束               |
| 选模和消耗可解释     | 返回分类来源、兜底原因、字典与路由版本、实际 Provider/模型及分项用量；未知用量保留 null                         |
| 接入保持最小增量     | 复用 Provider、单次 Runtime 和调用记录；新增应用内 routing 模块；数据库结构保持现状                             |

#### 1.1.2 架构与编码原则

| 原则                     | 设计约束                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------- |
| 分类、特征、选模分工清楚 | 模型识别两个标签，字典生成特征，确定性契约选择模型                                     |
| 复用现有执行内核         | 分类和主模型推理都通过 models 服务进入 llm Runtime；Runtime 保持业务无关               |
| 按需执行分类兜底         | JEV 优先，未通过门槛时顺序调用一次 Flash；Flash 单路可用于流程接入验证                 |
| 规则随代码管理           | 路由、门槛和默认值维护于类型化代码配置；Provider 凭据继续由现有模型管理保存            |
| 权限由服务端决定         | BFF 验证用户与作用域；内部分类授权由受信应用构造，浏览器只提交问题、上下文和主模型选择 |
| 每轮快照保持一致         | 受理时固定字典和配置版本；调用前校验 Provider 启用状态与能力                           |
| 状态与正文分开           | 分类事件用于进度展示，主模型输出用于回答；失败或不完整回答退出下一轮成功上下文         |
| 目录按实际职责建立       | routing 位于 Agent 内；跨应用通过 HTTP 契约协作                                        |

### 1.2 整体架构

浏览器和 BFF 继续使用已有 models/calls。Agent 的 routing 应用服务在主模型推理前完成分类、查表与选模；models 服务负责配置、凭据、授权及调用记录，llm Runtime 负责每次模型调用的生命周期。

JEV 与 Flash 分类输出同一业务对象。业务请求的 fixed/auto 只影响主模型选择；SC-39 使用专用 Flash 响应规则。分类与生成 Flash 可以复用一个 Provider，各自保留角色和调用标识。
