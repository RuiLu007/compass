需求简述

Compass 是电商经营分析 Agent。第 11 课建立统一的模型接入与单次执行能力，第 12 课在它前面增加两级意图分类、字典特征提取与模型选择，让用户通过同一个 Chat 入口获得适合当前任务的模型响应。

产品入口 用户操作 系统行为与结果
分析 Chat 输入业务问题，选择自动或指定主模型 一轮发送一次请求；服务端完成分类、查表、选模与一次主模型推理
路由详情 查看本次分类和模型选择 分别显示一级分类、二级场景、字典特征、实际模型、选模原因及分项用量
闲聊与范围外请求 提出日常闲聊或非业务任务，可预选 Pro 命中 SC-39 后使用 Flash 与独立提示词，温和说明经营分析范围并询问业务数据任务
停止生成 在分类或推理阶段停止 取消向当前调用传播，后续分类与推理停止，迟到片段退出当前页面显示

贯穿样例： 用户问“比较这份渠道汇总”，模型先返回 category_id 与 scene_id；字典查出任务类型、难度、响应方式和能力要求。自动模式按难度选择 Flash 或 Pro，固定模式使用用户指定主模型。若用户问“讲个故事”，系统按 SC-39 的独立规则使用 Flash，返回范围说明和业务任务引导。

本课聚焦分类到推理的最小闭环。真实取数、工具执行、Skill/subAgent/workflow 分派、多步计划及生成恢复由后续能力承接。本文为待实现设计；类型和核心算法包含伪代码，具体模型版本、字典字段与时间预算仍需接入确认。

1.2 整体架构

浏览器和 BFF 继续使用已有 models/calls。Agent 的 routing 应用服务在主模型推理前完成分类、查表与选模；models 服务负责配置、凭据、授权及调用记录，llm Runtime 负责每次模型调用的生命周期。

JEV 与 Flash 分类输出同一业务对象。业务请求的 fixed/auto 只影响主模型选择；SC-39 使用专用 Flash 响应规则。分类与生成 Flash 可以复用一个 Provider，各自保留角色和调用标识。

2. 详细设计方案

2.1 核心结构与请求流程

2.1.1 数据结构与记录归属

本课复用已有 Agent 数据库的 Provider 配置和 ModelCall 元记录。每次物理分类与推理各有调用标识，整轮阶段关联、分类和路由解释在响应与页面内存中组织。

本期不新增数据库表、列或迁移，不创建model_policy、model_execution、兼容组和多步骤记录。各次分类和推理复用现有ModelCall，保持purpose=test/chat与单次调用状态/用量记录。整轮call_id与物理调用ID的阶段关联、分类/特征/契约快照放本次响应与页面内存；不承诺整条链跨刷新查询、自动重放或后台续跑。

分类阶段由整轮call_id加固定阶段名派生稳定UUID子调用ID；主模型推理继续使用原call_id，复用现有ModelCall唯一键拒绝同阶段重复出站；重复ID发生冲突时整条请求停止，不自动重放历史正文。BFF不自动重试整个POST。无需建设跨进程完整路由事务或恢复幂等协议，后续确有持久化查询需求再增量设计。

对话、原始JEV响应、私有推理、凭据不新增持久化。Provider版本/绑定版本及每次实际用量使用已有字段；分类元信息只在响应中返回。首次受理使用配置快照，调用前Provider停用/绑定失效按已有约束拒绝，禁止悄悄换接入。

如果实施发现单次记录确需新增持久化字段，先补充数据库规范要求的owner、revision、SQL及恢复设计再实施；当前不预先安排数据库升级。

2.1.3 完整推理请求时序

状态图描述整轮应用流程，持久化继续记录各次物理调用。

正常与分类兜底

  1. 入口校验当前账号/租户/工作区、问题与上下文限制，读取字典和路由绑定快照。
  2. JEV在分类子时限内执行一次；通过两级分类门槛后继续。低置信、非法、父子不一致、上下文能力不足或不可用时进入一次Flash分类兜底。
  3. Flash结果按相同两字段Schema及父子关系校验；失败则结束，主模型推理零次。合法未识别场景继续按字典澄清模式处理。
  4. 字典提取特征；SC-39 优先绑定范围外 Flash，业务场景按 fixed/auto 路由契约选择模型，校验启用状态、用户选择、必需能力与输出约束。
  5. 调用现有Runtime一次，返回标准响应结构和各调用消耗。

最多一次JEV+一次Flash分类+一次主模型推理，共三次出站。无SDK隐含重试。本期不存在内部步骤模型分配。

时限、取消与未知结果

沿用180秒父时限上限；拟定分类子预算12秒，JEV最多3秒、Flash最多8秒，为主模型至少保留1秒，数值为实验起始值。每次出站使用父剩余时限和阶段时限的较小值，不重置总预算。修改仅涉及调用准备向已有CallPolicy传递子截止时间；Runtime内部单次机制保持现有语义。

取消/撤权/父时限耗尽立即停止本地流程，不再调用分类备路或主模型。JEV子调用超时或结果未知时，只有父请求仍有效、必要上下文适配且有剩余时限才允许Flash分类兜底；这是无业务副作用的异构分类路径，真实消耗保留未知。选定推理模型超时或结果未知直接结束。

主模型流式中断、Schema错误、凭据错误等复用既有错误状态与取消清理，不额外设计恢复矩阵。分类状态不当成业务正文。失败/不完整回答不进入下一轮成功上下文。

2.1.4 两级分类、字典与路由契约

2.1.4.1 分类模型输出

JSON / 1 LINES 
1{ "category_id": "business_channel", "scene_id": "SC-01" }

模型业务输出严格两个字段，均为字典登记ID：additionalProperties=false，无difficulty、task_type、action、model_id、Skill/工具或子任务数组。上例为设计示意，实际ID从现有场景字典冻结。

JEV在一个DecisionInput中提交两题：一级分类choice、二级场景choice。每题候选均来自服务端目录，场景描述包括父级定义；一次响应后校验场景属于分类。采用两题同时判断，正常路径一次出站。候选数、问题数及输入窗口沿用现有协议上限；超限直接交能完整处理的Flash，不裁剪场景目录或必要上下文。

JEV协议回答中的概率/可选confidence属于分类适配元信息，归一化后Intent只保留两字段。接受条件为类型、候选、父子关系合法，以及两题最高候选概率/间隔达到对应模型/模板/字典版本的代码默认门槛；confidence自报字段不单独作为准入依据。

Flash使用同一标签定义和严格JSON Schema，输出同样两个字段。JEV与Flash共享必要问题/成功上下文，但各自使用对应协议。模型版本、题目/提示模板、字典摘要与门槛绑定记录。Flash不需要返回模型自报难度或分类理由正文。

2.1.4.2 字典特征

场景工作簿继续维护分类、场景、特征及金标；运行时使用由其派生的只读JSON，不导入问题金标。拟新增apps/agent/scripts/export_routing_dictionary.py导出至routing/data/scenes.json并检查摘要一致性，运行应用无需读取XLSX。导出脚本与JSON随实现交付，当前文件均未创建。

字典项 语义
category_id / scene_id 一级归属、二级场景；scene_id全局唯一
task_type 如指标对比、诊断、整理、解释等场景特征
difficulty L1/L2/L3/undetermined，固定于本次字典版本
response_mode answer/clarify/refuse/handoff，决定本次响应约束
required_capabilities 真实必需的Schema/Thinking等能力；不因分类而新增工具执行
output_contract_ref 服务端已登记的回答/结构化响应约束

特征提取只执行dictionary[category_id, scene_id]与引用校验。未知键不临时补造字典行。字典登记“未识别/待澄清”场景用于Flash无法确定时的合法结果，随后按澄清响应契约处理；语法非法或两路调用失败返回分类错误。

一级分类、场景及特征的编辑真源保持工作簿；模型角色绑定和选模规则由类型化服务端代码配置维护。金标中的期望模型用于测试，不作为线上推理输入。现有40场景/88题保留，本次不编辑工作簿；其中旧复杂分类、业务分派和恢复题在实现前按当前PRD复核。

2.1.4.3 路由契约与静态绑定

本期路由输入为Intent、字典Feature、用户主模型选择、服务端Provider绑定和输入/能力约束。路由输出为选定模型身份/版本、Provider引用、选模原因、输出契约和调用时限。

条件 本次主模型选择
SC-39 闲聊 / 业务范围外 优先使用专用 Flash 绑定与独立范围引导提示词，reason=off_topic_flash
业务场景且用户fixed 使用用户指定的可用主模型；分类JEV/Flash独立
auto且L1 Flash配置绑定
auto且L2/L3 Pro配置绑定
auto且undetermined或需澄清 显式默认Flash响应绑定及字典对应的澄清/范围说明约束
绑定缺失、不可用或能力不足 明确拒绝，无第二个推理候选，不隐式换模型

固定模型仍接受能力校验。输出响应模式、格式与质量要求来自字典引用的服务端契约；模型选择不会把澄清任务改成凭空分析。复合输入命中已登记复合/待澄清场景，返回范围说明或澄清响应，本期不拆成多个执行步骤。

契约结构如SelectedRoute(provider_id, model_identity, output_contract, required_capabilities, reason, dictionary_version, routing_version)。不包含executor_kind、Skill、subAgent、workflow、step_plan、兼容组或恢复优先级。未来业务执行方式在后续需求设计，本期只保留稳定分类ID。

2.1.4.4 与Runtime的边界

分类器和本次推理都通过现有Runtime单次调用。推理请求只表达模型、完整输入、能力/输出契约和时限，不把分类枚举或字典传入Runtime策略。

本期只构造并验证一个选定推理模型。生成失败/未知结果按现有返回结束，不新增生成重试或模型替换。与后续可靠性方案的集成留到第14课，当前不预建恢复接口、通用执行协调器或候选CRUD。

2.2 运行依赖、配置与授权

复用 Python 3.13、FastAPI、Pydantic、现有 LiteLLM 与 SystemOne 适配器、PostgreSQL 调用记录。规则与阈值维护在服务端代码中，Provider 连接和凭据通过已有模型管理装配。

2.2.1 服务端代码配置

拟新增routing/config.py，以不可变类型化代码配置维护分类模式jev_with_flash/flash_only、JEV/分类Flash角色绑定、auto Flash/Pro角色绑定、分类子时限、模板版本、字典摘要和代码默认门槛；确定性选模规则维护于router.py。本期不增加路由策略表、草稿/修订模型、策略CRUD、启停API或编辑页面。

Provider连接及凭据继续用已有模型管理能力，代码配置只引用Provider身份；部署环境中不同的Provider ID通过已有环境配置装配到明确角色，规则、门槛和默认值留在代码中。密钥继续由已有Provider存储管理，不写入代码配置。

应用启动时验证字典和代码配置的结构一致性，每轮受理固定只读快照并通过现有模型服务校验Provider引用。规则和门槛随代码发布生效，绑定环境值变更随受控重启生效；通过正常发布回退配置。routing_version使用代码中配置版本或规范化内容摘要，仅用于响应追踪，不建立数据库修订及在线启停流程。

分类Flash与生成Flash可引用同一Provider，保留不同配置角色和call_id。用户fixed/路由auto只决定主模型，不改变分类配置。JEV按代码默认门槛完成流程；效果校准留后续课程，Flash单路可用于流程验收；缺少当前模式必需配置时明确不可用。

2.2.2 服务端分类授权

现有租户purpose=chat是请求来源，原ModelRepository.begin对Chat只允许GenerateInput和chat_visible模型。为统一推理入口的内部分类调用增加仅在进程内构造的RoutingGrant，包含actor、scope、call_id、stage和允许Provider；stage为intent_jev/intent_flash/inference。

BFF沿用module.analysis和models.invoke授权。routing服务基于受信Context和配置派生grant，ModelRepository.begin仅在带合法内部grant的分类路径允许DecisionInput或内部Flash；这两类分类Provider须enabled，但无需成为前端可选主模型。inference继续要求原Chat准入及chat_visible。统一推理HTTP DTO没有提交grant的字段，用户输入继续使用GenerateInput。

本地受控实验和已有平台Provider诊断使用purpose=test，统一推理链全部沿用purpose=chat及当前scope约束，无需新增purpose枚举、数据库CHECK或把租户请求伪装成平台测试。分类对象不提供数据授权；统一推理入口不接入取数/工具执行，无新增数据就绪声明契约。

代码配置另登记范围外响应的 Flash 角色与专用提示词版本；分类 Flash、业务生成 Flash 和范围外 Flash 可以复用 Provider，保留各自语义。

2.3 HTTP、响应与模块组织

2.3.1 统一推理API

前端发起推理统一复用 POST /api/web/v1/models/calls，BFF继续调用 Agent POST /v1/models/calls。静态和自动选模使用相同路径，服务端依次完成分类、字典特征提取、契约选模和一次推理，JSON/SSE由原input.stream决定。前端每轮只发送一次请求。

沿用现有鉴权、Same-Origin/CSRF、no-store和生成Schema校验；Agent复用服务令牌与受信Context。DTO唯一源为schemas.py与model_api.py，通过pnpm contracts派生。直接修改已有ChatCallInput及该路由的处理逻辑，不新增分析、路由、分类或路由测试端点。

2.3.3 统一流式协议与客户端迁移

在现有models/calls及ModelEvent协议上增量加入classification_status、route_selected。整轮仍只有一个start和唯一final，业务输出继续使用text_delta/tool_delta。start只声明call_id和整轮状态；实际主模型在route_selected之后确定，不预填Provider。BFF不再对auto请求预先绑定Provider，业务 fixed 请求在选模后校验实际主模型符合用户指定接入；SC-39 校验专用 Flash 绑定及 off_topic_flash 原因。

分类两字段与字典特征在route_selected和final返回，分类模型原始响应不向普通Chat暴露。所有公开事件使用整轮call_id，物理分类调用ID只进入分项元信息。主模型的文本/工具分片映射到同一事件流，不向前端发送分类模型的正文或子调用start/final。

JSON及final按§4.2统一演进；同步更新BFF生成Schema、事件校验、use-model-call和响应解析器，不另保留一条旧推理HTTP路径或通过参数分出低层调用模式。既有Provider诊断保留原CallResponse及单次ModelEvent，可复用基础事件类型；在DTO中清楚区分诊断结果和整轮推理结果。

断连和资源清理复用现有模型服务生命周期，取消覆盖当前分类或推理。统一入口将最终CallResponse组装入整轮final；不新增流式恢复或持久化重放协议。

安全错误码包括intent_unavailable、intent_invalid、dictionary_unavailable、route_binding_missing和route_capability_mismatch。开始流前按现有401/403/422/409/503返回；开始后通过唯一final报告错误。主模型已输出后的失败保留incomplete，不重发。
